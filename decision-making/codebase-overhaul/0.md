# 0차: 코드베이스 정비 메타 의사결정

## 배경

nai-tag-builder v1.0→v2.9 동안 누적된 기술 부채를 정리하려 한다. ARCHITECTURE.md에 R1~R5 리팩토링 방향이 이미 문서화되어 있고, HANDOFF에 다음 단계가 명시되어 있다.

n차 의사결정 프로세스를 코드 작업에 처음 적용한다. 기존 프로세스는 정보/설정 아키텍처(문서 역할, 파일 구조, 스킬 설정)를 위해 만들어졌으므로, 코드 작업의 특성(변경 간 의존성, 동작 보존 검증, 사용자 데이터 마이그레이션)에 맞게 적응이 필요하다.

사용자 동기: (1) 디버깅이 너무 힘들어서 구조 정리가 필요, (2) 로드맵 기능 추가를 위한 기반 구축.

## 결정 요약

### 결정 1 — 작업 명칭과 범위

명칭: 코드베이스 정비 (codebase-overhaul).
4개 유형(순수 리팩토링, 기능 추가, 버그 수정, 클린업)을 하나의 의사결정 프로세스로 통합. 프로젝트 규모(src 15파일, 메인 372줄)에서 유형별 분리는 과잉이고, 항목 간 의존 관계가 있어 함께 다뤄야 순서를 최적화할 수 있다.

### 결정 2 — 프로세스 적응 (탐색→심화→구현→확장)

탐색에 추가:
- 의존성 매핑: 항목 간 선후 관계를 그래프로 정리. 순서 결정 근거.
- Breaking change 분류: 각 항목에 [internal](내부 구조만 변경) 또는 [external](사용자 데이터/동작에 영향) 태그.

심화에 추가:
- 검증 기준: 각 결정 확정 시 "무엇으로 동작 보존을 검증하는가"를 함께 기록.
- 마이그레이션 전략: [external] 항목에 한해 기존 데이터 호환 방안 조사/확정.

구현에 추가:
- 테스트 동반: 각 구현 단계에서 해당 영역의 테스트를 함께 생성. 별도 "테스트 구축 단계" 없음.
- 검증 실행: 구현 직후 심화에서 정한 검증 기준 실행, 결과 기록.

확장: 변동 없음.

### 결정 3 — 기존 계획(R1~R5)의 위치

ARCHITECTURE.md R1~R5를 1차 탐색의 입력으로 삼는다. 백지 시작 아님.
R1~R5에 HANDOFF "다음" 항목과 클린업 항목을 병합하여 전체 작업 목록 구성.
우선순위와 순서는 1차에서 재검토.

### 결정 4 — 1차 탐색의 설계

1차 탐색 산출물:
1. 전체 작업 항목 목록 (R1~R5 + HANDOFF + 클린업, 병합/분할 가능)
2. 각 항목의 접근 방식 잠정 결정 + [internal]/[external] 태그
3. 항목 간 의존성 그래프
4. 사용자 동기 기반 우선순위 배치
5. 심화로 승계할 미결 항목
