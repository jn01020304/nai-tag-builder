## 항목 1: DB 구조 설계

### 현황

db.ts에 `TagEntry` 인터페이스가 이미 정의되어 있다:
```
{ id(auto), keyword, category, weight, isEnabled, isNegative, description?, createdAt }
```
Dexie `tags` 테이블도 v1에서 생성됨. 그러나 코드 어디에서도 사용하지 않는다.

현재 태그는 `basePrompt` 문자열 안에 쉼표 구분 텍스트로 존재:
- `1girl, solo, 1.5::artist:riichu::, ...`
- 가중치: `weight::tag::` 또는 `{{tag}}` / `[[tag]]`

intensityParser.ts가 이 문자열을 Token[]으로 파싱하여 하이라이팅에 사용하지만, 구조화된 태그 객체로 변환하지는 않는다.

### 문제

기존 TagEntry 스키마와 실제 프롬프트 형식 사이에 갭이 있다:
- TagEntry에 `weight` 필드가 있지만, NovelAI 가중치 문법(`1.5::tag::`)과 매핑이 정의되지 않았다
- `category`의 값 체계(어떤 카테고리가 존재하는지)가 미정
- 태그 순서가 중요한데(NovelAI는 앞쪽 태그에 더 가중), TagEntry에 순서 필드가 없다
- 캐릭터별 태그 소속(`CharacterEntry.caption`)과 TagEntry의 관계가 미정

### 잠정 결정

기존 TagEntry 스키마를 확장한다:

```typescript
interface TagEntry {
  id: number;           // auto-increment
  keyword: string;      // "artist:miv4t", "1girl", "blonde hair"
  category: string;     // "artist", "character", "style", "quality", "body", "clothing", ...
  weight: number;       // 1.0 = 기본, 1.5 = 강조, -3 = 억제
  isEnabled: boolean;   // false면 컴파일 시 제외
  isNegative: boolean;  // true면 negativeBase에 편입
  order: number;        // 프롬프트 내 위치. 낮을수록 앞
  scope: string;        // "base" | "char_{id}" — 소속 (base prompt vs 캐릭터)
  description?: string;
  createdAt: number;
}
```

추가 필드 2개: `order`(순서), `scope`(소속).

2순위의 프롬프트 컴파일러가 이 TagEntry[]를 읽어 NovelAI 문법 문자열로 조립한다. 그때까지 TagEntry는 저장 계층으로만 존재하고, UI 입력은 기존 textarea 방식을 유지한다.

### 심화 미결

- category 값 체계: Danbooru 태그 분류를 따를지, 커스텀 분류를 쓸지
- 기존 프리셋의 basePrompt 문자열 → TagEntry[] 마이그레이션 전략
- TagEntry와 MetadataState.prompt 사이의 동기화 방향: TagEntry가 source of truth인가, basePrompt가 source of truth인가

## 항목 2: 디자인 시스템 구성

### 현황

theme.ts에 ThemeColors 인터페이스(22색)가 있고, useDynamicTheme()이 NovelAI 페이지에서 실시간 스크래핑한다. 3개 스타일 함수(inputStyle, labelStyle, smallBtnStyle)가 export된다.

컴포넌트별 inline style을 직접 작성하는 패턴:
```tsx
<div style={{ display: 'flex', gap: '8px', fontSize: '12px', color: theme.subtext0 }}>
```

공유 컴포넌트: CollapsibleSection 1개뿐. 나머지는 각 컴포넌트가 독립적으로 스타일을 정의.

### 문제

- 같은 패턴의 스타일이 여러 컴포넌트에 중복 (row, checkbox row, number input 등)
- 새 기능 추가 시 매번 inline style을 처음부터 작성해야 함
- 태그 칩, 슬라이더, 카드 등 2~3순위 UI에 필요한 공용 컴포넌트가 없음

### 잠정 결정

외부 컴포넌트 라이브러리는 도입하지 않는다. 이유:
- 북마클릿이므로 번들 크기가 중요 (현재 350KB)
- NovelAI 테마를 실시간 스크래핑하는 특수 구조 — 외부 라이브러리의 테마 시스템과 충돌
- 현재 inline style 패턴이 이 프로젝트에서 잘 작동하고 있음

대신 내부 공용 컴포넌트를 점진적으로 추출한다:
- `TagChip` — 태그 표시/편집 단위 (2순위 태그 UI의 기본 블록)
- `SliderInput` — 가중치 조절용
- `NumberInput` — 현재 GenerationParams/AutoGeneratePanel에서 중복되는 패턴
- `CheckboxRow` — AdvancedParams에서 반복되는 패턴

시기: 2순위 항목 구현 시 필요에 따라 추출. 미리 만들지 않음.

### 심화 미결

- tagPositiveBg/tagNegativeBg 색상이 theme에 이미 있지만 사용처가 없다. TagChip이 이 색상을 사용할 것인가
- 태그 칩의 시각 디자인: 텍스트만? 아이콘? 카테고리별 색상?

## 항목 3: NovelAI API 연동 테스트

### 현황

현재 NovelAI와의 통신 경로는 클립보드 paste 한 가지:
1. buildCommentJson → pngEncoder → Comment tEXt 청크가 포함된 PNG blob 생성
2. dispatchPasteEvent → 클립보드에 PNG를 넣고 paste 이벤트 발행
3. NovelAI 프론트엔드가 paste를 감지하여 Import Metadata 모달 표시
4. 사용자가 "적용"을 누르면 NovelAI가 자체 백엔드에 생성 요청

직접 API 호출은 없다. NovelAI의 이미지 생성 API는 공식 문서화되어 있지 않으며, 웹 클라이언트의 네트워크 트래픽에서 역공학해야 한다.

### 문제

- API 엔드포인트, 인증 방식, 요청/응답 형식이 공식 문서에 없음
- API 키 또는 세션 토큰이 필요할 가능성이 높음 — 북마클릿에서 어떻게 안전하게 다루는가
- NovelAI TOS(이용약관)에서 API 직접 호출을 허용하는지 불명확
- 현재 paste 경로가 이미 동작하고 있어서 API 연동의 필요성 자체를 재검토해야 함

### 잠정 결정

API 직접 연동은 1순위에서 제외한다. 이유:

1. 현재 paste 경로가 정상 동작하며, 사용자의 핵심 워크플로우(프롬프트 편집 → 이미지 생성)를 이미 지원
2. API 역공학은 NovelAI 업데이트마다 깨질 위험이 있다
3. 공식 API 문서가 없는 상태에서 TOS 위반 여부를 확인할 수 없다
4. 2순위의 "이미지 생성 호출 및 결과 출력"에서 다시 검토하되, 그때도 paste 경로 확장(자동 Apply + Generate 클릭 자동화)을 먼저 시도

대신 1순위에서는: NovelAI 프론트엔드의 DOM 구조를 조사하여 "Generate 버튼 자동 클릭", "생성 완료 감지", "결과 이미지 캡처" 가능 여부를 확인한다. 이것이 API 직접 호출보다 현실적이고 안전하다.

### 심화 미결

- NovelAI 프론트엔드 DOM에서 Generate 버튼을 찾아 클릭하는 것은 이미 useAutoGenerator에서 하고 있다 — 범위가 겹치는가
- "이미지 생성 호출 및 결과 출력"(2순위)을 paste 경로로 완전히 대체할 수 있는가, 아니면 API가 결국 필요한 시점이 오는가

## 의존성 분석

```
DB 구조 설계 ─→ 프롬프트 컴파일러 (2순위)
             ─→ 태그 가중치 편집 UI (2순위)

디자인 시스템 ─→ 태그 가중치 편집 UI (2순위)
             ─→ 3순위 UI 전체

API 연동 ─→ 이미지 생성 호출 (2순위)
```

DB 구조가 가장 많은 후속 작업의 전제. 디자인 시스템은 구현과 동시에 진행 가능. API 연동은 실질적 차단 요소가 아님 (paste 경로로 우회 가능).

## 실행 순서 잠정

1. DB 구조 설계 — TagEntry 스키마 확정 + 프롬프트 문자열 ↔ TagEntry[] 변환 로직
2. 디자인 시스템 — TagChip 컴포넌트 (DB 구조와 동시 진행 가능)
3. API 연동 테스트 → DOM 자동화 조사로 범위 재정의

## 결정 요약

- 결정 1: TagEntry 스키마를 `order`, `scope` 필드로 확장. 기존 db.ts 정의를 발전시킨다.
- 결정 2: 디자인 시스템은 외부 라이브러리 없이 내부 공용 컴포넌트를 점진 추출. 미리 만들지 않고 2순위 구현 시 필요에 따라.
- 결정 3: NovelAI API 직접 연동은 1순위에서 제외. DOM 자동화 조사로 범위 재정의.
- 결정 4: 실행 순서는 DB 구조 → TagChip → DOM 자동화. DB가 가장 많은 후속 작업을 차단.

## 심화로 승계할 미결

- TagEntry의 category 값 체계 (Danbooru 분류 vs 커스텀)
- basePrompt ↔ TagEntry[] 변환 전략과 source of truth 결정
- 기존 프리셋 마이그레이션 (문자열 → 구조화 태그)
- TagChip 시각 디자인 (카테고리별 색상, 가중치 표시 방법)
- DOM 자동화의 구체 범위 (Generate 클릭 자동화는 이미 있음 — 중복 확인)
